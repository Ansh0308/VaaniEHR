# FHIR_GAPS.md - what the ABDM profiles ask for that VaaniEHR does not have (Phase 9A, ADR-D40)

Each row is a requirement or must-support element of the ABDM IG 6.5.0 profiles (OPConsultRecord, PrescriptionRecord, DocumentBundle, Patient, Practitioner, Encounter, Condition, Observation, AllergyIntolerance, MedicationRequest) that we cannot meet with data we hold. Rule: nothing is invented to close a gap. Where the IG allows text only or leaves the element optional, we use that; otherwise the gap is listed here. The validator's verdict for the golden bundles is in `docs/FHIR_MAPPING.md` and the report of the run (ADR-D40): **0 errors** for every good bundle; the warnings left are the Practitioner identifier code (gap 2) and nothing else.

| # | Profile element | What the IG wants | What we have | What we do | Closes with |
|---|---|---|---|---|---|
| 1 | `Patient.identifier` (1.., MS) with `type` (extensible, `ndhm-identifier-type-code`) | the patient's ABHA number / health id (system `https://healthid.ndhm.gov.in`) in the IG examples | only the clinic's own patient id | identifier of type `MR` (HL7 v2-0203, used in the IG's example) in OUR namespace `https://vaaniehr.invalid/fhir/id/patient`; **no ABHA number is written** | Phase 12. Phase 9B (ADR-D42) stores the ABHA **address** and only a salted hash of the number, never the number, so there is nothing to write here; the builder is unchanged |
| 2 | `Practitioner.identifier` (1.., MS) with `type` (1..) | the doctor's HPR id or licence number (`MD`, system `https://doctor.ndhm.gov.in` in the examples) | only our user id | `type.text` only ("VaaniEHR user id (not an HPR id or a licence number)"), our namespace. The validator **warns** "No code provided" for this: kept, not hidden | HPR id from the owner / ClinicOS integration (Phase 12); a clinician or the institution must supply real registry ids |
| 3 | `Composition.custodian`, `Organization` (facility, HFR id) | the facility as custodian with its Health Facility Registry id | a clinic name in ClinicOS, no HFR id | not populated (custodian is optional) | facility registry id from the owner; Phase 12 |
| 4 | Codes for symptoms, conditions, allergies, observations, medicines (`Condition.code`, `Observation.code`, `AllergyIntolerance.code`, `MedicationRequest.medication[x]`: SNOMED CT, ICD-10, LOINC) | coded concepts (coding is 0.. so text-only is valid) | internal concept ids (unreviewed draft list), medicine master with empty `snomed_code` / `atc_code` | text only. No code is written | SNOMED CT licence (OWNER_ACTIONS), reviewed concept list (OCI-017), reviewed medicine codes |
| 5 | `MedicationRequest.dosageInstruction` structure (`timing`, `route`, `additionalInstruction`, `method`: SNOMED) | structured dosage | dose, a frequency code (OD, BD...) and a duration as text; the master's route is empty | `dosageInstruction.text` only | clinician review of the frequency list; coded route; SNOMED |
| 6 | `Observation.value[x]` Quantity with units (vitals) | measured values with units | a vital is one free-text string | `valueString` | structured vital capture (a later phase) |
| 7 | `Bundle.meta.security` (MS) | a confidentiality label (the IG example uses v3-Confidentiality `V`) | no policy decision | not populated (optional) | the owner's data-protection decision (OCI-016) |
| 8 | `Bundle.signature` | an electronic signature (in the IG examples; not required) | a password re-entry attestation, stored as `Composition.attester` (legal) | not populated | a signing service, if ever needed (Phase 12+) |
| 9 | `Encounter.type`, `serviceType`, `priority`, `reasonCode`, `diagnosis.use` (SNOMED) | coded encounter details | none collected | not populated (all optional); `class = AMB` only | later, with clinician input |
| 10 | Sections for family history, referral, procedure, follow-up, order document | those sections | not collected in this prototype | not built (sections are 0..1) | later phases |
| 11 | `Practitioner.qualification`, `telecom`, `gender`, `birthDate`, `photo` | optional MS fields | name only | not populated | ClinicOS integration |
| 12 | `Patient.address` (MS) | address | not held | not populated | ClinicOS integration |
| 13 | Language of the text | `language` | a visit mixes Gujarati and English | no `language` element | decided with the Gujarati reviewer |
| 14 | `Patient.telecom` phone with country code | `+91...` in the examples | 10 digits (ClinicOS keeps the first 10 digits, India only, CLINICOS_INTEGRATION_FACTS) | `+91` is added in front | confirm when non-Indian numbers matter |
| 15 | PrescriptionRecord `Binary` section entry (a signed PDF of the prescription) | an optional `Binary` entry | none | not built | a printable prescription (not in the PRD for this phase) |

None of these block validation: every good golden bundle has 0 errors against the IG. They limit **how useful** a bundle is to another system (no ABHA, no HPR, no codes) and they are the honest state of a prototype with simulated data.
